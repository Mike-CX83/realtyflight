# FINAL RECOMMENDATION

**Status:** v1.0 — issued 2026-08-14 after Phases 1–7. Evidence base: docs 00–10 + RESEARCH_LOG (every load-bearing claim primary-sourced and dated). Two decisions are presented as recommendations with alternatives per the project's own rules (G1 foundation strategy, G2 hardware); everything else is decided here.

---

## 1. Executive summary (plain language)

Build a small, governed system where **language proposes, rules decide, a human authorizes, and a state machine flies** — first against a fake drone in tests, then a PX4 drone in Gazebo, then the virtual ANAFI Ai in Parrot's own simulator, and only then the real ANAFI Ai outdoors. Your drone can do the job: its 2026-maintained SDK exposes bracketing, RAW, gimbal, speed-bounded moves, geofence and return-home — everything the exterior-photography mission needs — but it cannot do autonomous indoor flight (Parrot says so directly), so interiors are out of this capstone. The five collected repos contribute one serious reference (MDS's Simurgh governance layer), one cautionary tale (dronesphere's empty validator), two teaching examples, and one dev-tooling library; none contains the photography mission layer, which — along with the backend-neutral core — is the genuinely new thing you build and defend. Total MVP cost: $0 plus modest LLM API spend; one Linux box unlocks the physical-drone stretch.

## 2. Answers to the 25 required questions

1. **Exact ten-month MVP?** Docs 00 §2 / 01 §6: typed/spoken request → validated `MissionPlan` → human approval → simulated PX4 flight (takeoff, orbit with structure framing, 8+1 bracketed captures, RTH, land) with live dashboard, fault drills (GPS/link/battery/abort/override), step-linked media, and a fully replayable audit log; CI-tested. Stretch: identical mission on Sphinx, then one bounded physical ANAFI flight.
2. **Deliberately deferred, why?** Indoor/GPS-denied autonomy (platform-impossible on ANAFI — Parrot staff; SLAM stacks GPL/dormant); subject tracking (onboard_tracker exists but unneeded for exterior packages); CV-based framing (geometric orbit suffices — industry shot lists are geometric); photogrammetry/3D (AGPL + scope); RAW pipeline beyond capture (MLS delivers JPEG); BVLOS/unattended ops (Part 108 not final; RPIC required regardless); swarm (excluded by charter).
3. **What runs where?** 08 §11: browser = UI+dictation; Python backend = planner/validator/approval/engine/events/media; Linux box = SITL, Sphinx, Olympe, drone WiFi; flight controller = stabilization + native failsafes only; no companion computer in MVP; LLM cloud or local behind one interface.
4. **LLM local, cloud, or neutral?** Provider-neutral via PydanticAI: cloud model for quality (Anthropic/OpenAI), Ollama structured outputs as local/offline fallback. The safety case never depends on which — the validator is the gate.
5. **Typed mission representation?** 08 §3: Pydantic v2 `MissionPlan` — envelope (property/boundary/home, limits, failsafe policy) + discriminated-union steps, `extra="forbid"`, unit-suffixed fields, server-side plan hash; JSON Schema exportable.
6. **Permitted primitives?** `takeoff, goto, orbit, set_gimbal, capture_photo(single|bracket3|bracket5), hold, return_home, land` (+`preflight` implicit), compiled from a named shot library (front_34_elevated, lot_overhead, exterior_orbit…). Vocabulary grows only by adding typed steps + rules + tests.
7. **Creative request → deterministic steps?** LLM maps intent to shots/primitives inside the vocabulary (creativity = shot selection, angles, sequencing); shot compiler expands to primitives; validator + operator brief make every consequence inspectable. Nothing creative survives past the schema boundary.
8. **What validates independently of the LLM?** The 17-rule deterministic catalog (08 §4): schema, geometry-in-meters (Shapely, AEQD local frame), kinematic caps, sequence sanity, battery/energy, telemetry freshness, capability checks — run at plan time and re-run per dispatch.
9. **What requires human approval?** Every flight-affecting plan (hash-bound, 300 s TTL, re-approval on any change); real-flight profile additionally requires a typed confirmation (ENV-01); resume-after-pause re-runs the dispatch gate.
10. **State/retries/timeouts/cancellation/recovery?** 08 §5: evidence-gated state machine; idempotent dispatches, ≤2 retries on timeout only; per-step and per-state watchdogs; abort preempts the running task and commands the backend; recovery = deterministic policy responses, then operator.
11. **Manual override?** Suspends dispatch, cancels queue, mission → `manually_overridden` (terminal); on ANAFI the mechanism is SkyController piloting-source reversion (modal — verified), rehearsed on the ground before any flight; autonomy never reclaims the aircraft programmatically.
12. **Network/GPS/localization/perception/camera/command failure?** Failure-mode table 10 §3 + FailsafePolicy in every plan: GPS→hold 10 s→RTH; link→backend-native auto-RTH + no dispatch on stale state; battery→reserve-triggered RTH; camera/capture failure→step fault→retry once→operator; command failure→bounded retries→hold. No silent continues; no synthetic telemetry.
13. **Indoor vs outdoor failsafes?** Outdoor: RTH-centric as above. Indoor: **unsupported by design in MVP** (RTH is unsafe indoors and the platform can't do indoor autonomy anyway); the policy enum contains only evidence-backed behaviors so "indoor RTH" cannot be configured by accident.
14. **Backend contract shared by sims and drones?** 08 §6 `DroneBackend` protocol: connect/preflight/motion/gimbal/capture/RTH/land/abort + telemetry stream + media fetch + capabilities + typed error taxonomy; orbit lives in the engine (waypoint ring) so all backends share it; one contract-test suite certifies Fake, PX4, Olympe alike.
15. **Primary simulator, why?** PX4 SITL v1.17 + Gazebo Harmonic (doc 05): current-stable + LTS, lockstep-deterministic, headless CI, typed `failure` injection matching our fault list, gimbal airframe, CC0 house world — the only candidate scoring on every requirement. Known cost accepted: photo capture via gz topic, not MAVLink camera.
16. **Can Sphinx validate the actual ANAFI path?** Yes — it runs the real ANAFI Ai firmware (firmware-in-the-loop), simulates all cameras, injects GPS/wind/battery faults, and Olympe talks to it exactly as to the aircraft (IP-address switch). Two OQs to spike week-1 on the box: in-sim camera2 capture + media download; link-loss injection method.
17. **Can ANAFI Ai meet photography + autonomy requirements?** **Conditional go** (doc 06): yes for outdoor exterior packages via code-verified APIs (camera2 bracketing/DNG/manual exposure, gimbal, extended_move_to, geofence, RTH suite); no for indoor autonomy and no follow-me (onboard_tracker instead, post-MVP); conditions C1–C5 (Linux box, Sphinx spikes, backend-neutral core, G5 protocol, no indoor claims).
18. **If not, what custom hardware?** None now. Exit ramp documented (doc 07): PX4 dev-kit-class build only if a defined trigger fires (Gate G3); our PX4 sim backend is already the software half of that path.
19. **Which existing repos remain?** All five remain on disk untouched (nothing deleted): MDS = reference/donor per G1; dronesphere = concepts-only reference (reimplement — unlicensed); LLM-controlled-drone + FPV-Drone-AI-Agent = read-only references; claude-power-user = dev tooling (prefer upstream obra/superpowers). Dispositions final in docs 02 §6 / 03.
20. **Newly discovered projects: adopt/study/reject?** Adopt: PydanticAI, Pydantic, python-statemachine, Shapely, FastAPI, structlog, MAVSDK, Olympe, MapLibre, Rerun (post-MVP), faster-whisper, OpenCV(+Mertens), exiftool. Study: AUSPEX "Say'n'Fly" + RoboGuard (cite as the academic grounding), TypeFly (vocabulary idea), MDS Simurgh (governance reference), anafi_ros (BSD ROS2 bridge, if ever needed), qgc-mavlink-converter (FlightPlan format). Reject with reasons: LangGraph/CrewAI-as-architecture, Temporal, OPA, Foxglove v2, Grafana/OTel for MVP, Ultralytics-in-core (AGPL), pyiqa (NC), AirSim/Colosseum/Flightmare/Isaac (doc 05), Vosk, DroneKit-based stacks. Full tables: doc 04.
21. **What custom middleware must we create?** (a) `MissionPlan` schema + shot library; (b) policy engine + geo module; (c) mission state machine/executor with evidence gating; (d) `DroneBackend` contract + three adapters (Fake, PX4, Olympe); (e) approval service; (f) event store/audit + replay; (g) planner prompt+repair layer; (h) dashboard. Estimated 4–7 kLOC Python + 2–3 kLOC TS — sized for this team precisely because everything heavier was delegated to vetted OSS.
22. **How is media quality and mission success evaluated objectively?** Mission success = event-log assertions (every step evidence-complete, zero policy violations at dispatch, media count = plan count, terminal state `completed`) — machine-checkable in CI. Media: MVP = deterministic trio (Laplacian blur threshold, histogram clipping bounds, telemetry tilt ≤2°) recorded per image; POST = retake automation on those flags; explicitly not learned IQA (license + explainability).
23. **How tested automatically before physical flight?** 08 §10 pyramid: unit (rules/schema/state machine incl. abort preemption) → backend contract suite → headless lockstep SITL scenarios with fault injection per PR/nightly → planner eval set (≥95% valid, adversarials must die in the validator) → G4: identical mission + media on Sphinx. Physical flight adds margin, never first-time behavior.
24. **Highest risks?** (doc 10): R7 scope creep (H×H — gates + charter exclusions); R8 team throughput (M×H — vertical slices, MDS demo as onboarding); R1 Parrot platform decay (M×H — backend-neutral core + PX4 ramp); R2/G2 Linux box (M×M/H — MVP immune, stretch exposed); R9 license contamination (M×M-H — landmine list + PR review); R11 override semantics on real aircraft (M×H — ground rehearsal, G5).
25. **What evidence would change the architecture?** Sphinx spikes failing (→ PX4-physical exit ramp via G3); PydanticAI/structured-output reliability <95% after prompt iteration (→ Instructor / grammar-constrained local decoding); gz frame-grab unusable (→ Webots camera sandbox or Classic-era typhoon only as last resort, re-scored); MDS license posture changing or local needs diverging (→ revisit G1); FAA Part 108 finalization (→ Tier-3 framing only); any deterministic-safety requirement proving untestable (→ stop-and-redesign, per charter it outranks features).
